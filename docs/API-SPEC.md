# API Specification

## Style

REST API using FastAPI.

Version the API, e.g. `/api/v1`.

Use JSON for normal API payloads.

Use multipart upload endpoints for documents.

## Principles

- consistent status codes
- consistent validation errors
- pagination for lists
- server-side filtering
- server-side authorization
- idempotency for sensitive operations where appropriate
- transaction boundaries in service layer
- OpenAPI documentation generated by FastAPI

## List Endpoints

Support common parameters where applicable:
- page
- page_size
- search
- status
- date_from
- date_to
- sort_by
- sort_order

Do not allow arbitrary SQL field sorting.

Whitelist sortable fields.

## Business Operations

Prefer explicit action endpoints for state transitions when appropriate.

Examples:
- POST `/government-loads/{id}/accept`
- POST `/government-loads/{id}/reject`
- POST `/milling-batches/{id}/complete`
- POST `/rice-quality/{id}/approve`
- POST `/dispatches/{id}/dispatch`
- POST `/delivery-receipts/{id}/confirm`
- POST `/government-claims/{id}/submit`
- POST `/government-claims/{id}/approve`
- POST `/payments`

The exact endpoint structure can be refined during implementation, but arbitrary PATCH of status must not bypass business rules.

## Error Contract

Return safe, structured errors containing:
- machine-readable code
- user-safe message
- optional field errors

Do not expose stack traces.

## Authorization

Every protected endpoint must enforce authorization server-side.

Never rely on hidden frontend buttons for security.
